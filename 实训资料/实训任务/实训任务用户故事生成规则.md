# 实训任务用户故事生成规则

> 本文件是实训任务用户故事的编写规范。以 `第一天用户故事.md` 中 M01 任务为范本提炼，用于指导 M02—M12、E01—E06、G01—G03 共 22 个剩余任务的用户故事编写。

## 一、本文件给谁看

**读者**：实训任务设计人员。

**职责**：依据三日方案第六部分的任务详情，结合平台已有功能，为每个任务编写一份面向开发人员的用户故事文档。

**不要求**：读者不需要写代码，但需要能描述清楚"平台要做什么、学员填什么、系统校验什么、评分怎么算"。

**产出**：每个任务一份用户故事，按本文件第二节的结构编写，存入 `docs/实训设计/` 目录，文件名格式为 `第N天用户故事.md`（同一天多个任务合并在一份文件里）。

## 二、读者需要看哪些内容才能动手

在编写任意一个任务的用户故事前，读者**必须**先阅读以下三份文件：

| 顺序 | 文件 | 从中获取什么 |
| --- | --- | --- |
| 1 | `docs/培训方案/高职教师AI实操培训三日方案.md` 第六部分 | 该任务的标签、输入材料、操作任务、阶段成果、任务专用评分项——这是用户故事的**唯一事实来源**，用户故事不得偏离 |
| 2 | `第一天用户故事.md` M01 部分 | 用户故事的**完整结构和写法范本**，照此结构填写 |
| 3 | `小组复核功能设计.md` | 该任务的小组复核模板怎么配——字段类型有哪些、角色确认怎么走、passRule 怎么写 |

读完这三份文件后，读者应能回答以下问题，回答清楚即可动手编写：

1. 这个任务要让学员解决什么真实教学问题？（→ §1 任务设计意图）
2. 平台要给学员提供哪些输入材料和操作入口？（→ §3 平台功能）
3. 学员要填什么字段、作什么判断、系统怎么校验？（→ §3 + §5）
4. 判断分类有哪几类、各类边界怎么定？（→ §3 对应小节）
5. 小组复核要复核什么、字段模板怎么配？（→ §3.5 + `小组复核功能设计.md`）
6. 评分五项标准的每一项，平台靠什么数据校验？（→ §4.1）
7. 需要提供哪些参考事实或示例数据供评分逻辑使用？（→ §4.2）
8. 成果数据结构长什么样？（→ §5）

## 三、用户故事的固定结构

每个任务的用户故事**必须**包含以下 5 节，顺序和标题固定，不得增删或改名：

```
## 一、任务 {编号}：{任务名称}

### 1. 任务设计意图
### 2. 任务信息
### 3. 平台需要提供的功能
### 4. 评分逻辑
### 5. 成果数据结构
```

下面逐节说明填写规则。

---

### §1 任务设计意图

**写什么**：用 3 段话说明这个任务为什么存在。

**必须包含的 3 段**：

| 段落 | 标题 | 内容 | 字数建议 |
| --- | --- | --- | --- |
| 1 | 要解决的问题 | 高职教师在什么工作中遇到什么困难，现状有什么风险 | 50—80 字 |
| 2 | 任务目标 | 让教师通过什么操作，建立什么意识或形成什么能力 | 40—60 字 |
| 3 | 能力培养 | 列出 2—4 个核心技能点，用顿号分隔 | 15—30 字 |

**写法要求**：

- "要解决的问题"必须指向**真实教学场景**，不写"提升 AI 素养"这类空泛目标。
- "任务目标"必须对应**可观测的操作**（提问、标注、修正、对比、配置等），不写"理解""掌握"等不可观测动词。
- "能力培养"的技能点必须与三日方案中该任务的"核心技能点"一致，可直接引用。

**范本**（M01）：

> **要解决的问题**：高职教师在备课、课堂安全、教研和成绩解读中越来越多地使用 AI，但缺乏识别大模型幻觉的能力，容易把 AI 编造的内容当作事实直接用于教学。
>
> **任务目标**：让教师用 4 个真实教学问题向 AI 提问，亲手核验 AI 回答，建立"AI 生成内容必须由教师核验后使用"的基本意识。
>
> **能力培养**：事实核验、引用核验、冲突识别、结论修正。

---

### §2 任务信息

**写什么**：一张标签表，直接从三日方案第六部分该任务的标签表复制。

**必须包含的行**：

| 标签 | 来源 |
| --- | --- |
| 编号 / 性质 / 难度 | 三日方案该任务标签表 |
| 协作方式 | 三日方案该任务标签表 |
| 教学场景 | 三日方案该任务标签表 |
| 核心知识点 | 三日方案该任务标签表 |
| 核心技能点 | 三日方案该任务标签表 |

**写法要求**：

- 逐字复制三日方案的标签内容，不改写、不合并、不新增。
- 如果三日方案的标签表有时长行，这里不单独列时长（时长在日程表中已有）。

**范本**（M01）：

| 标签 | 内容 |
| --- | --- |
| 编号 / 性质 / 难度 | M01 / 必修 / 入门 |
| 协作方式 | 个人判断、小组复核 |
| 教学场景 | 备课核验、课堂安全、科研引用、成绩解读 |
| 核心知识点 | 大模型幻觉、事实与观点、证据来源、安全边界 |
| 核心技能点 | 事实核验、引用核验、冲突识别、结论修正 |

---

### §3 平台需要提供的功能

**写什么**：把三日方案中该任务的"输入材料"和"操作任务"翻译成平台要做的具体功能，每个功能一个小节。

**这是用户故事的核心，也是开发人员的主要实现依据。**

#### 3.0 如何拆分小节

按以下顺序拆分，每个操作步骤对应一个功能小节：

1. **输入/提问入口**：学员拿到什么材料、向 AI 提什么、平台保存什么。
2. **操作工具**：学员在平台上做什么操作（标注、填写、对比、配置等）。
3. **判断/记录**：学员对结果作什么判断、填什么字段、系统怎么校验。
4. **修正/迭代**：学员怎么改、改前后怎么留痕。
5. **小组复核**：如果该任务协作方式含"小组复核/小组互评/小组共评"，必须配小组复核功能。

每个小节的标题格式为 `3.N 功能名称`，名称用动词+对象，如"提问入口""标注工具""判断与核验记录"。

#### 3.1 每个功能小节必须包含的内容

| 内容 | 说明 |
| --- | --- |
| **功能描述** | 1—2 句话说明平台要做什么 |
| **具体内容/数据** | 如果平台要预置问题、材料、选项、字段，用表格列出 |
| **设计要求** | 用列表说明平台必须满足的约束，如校验规则、保存要求、禁用条件 |

**范本**（M01 §3.1 提问入口）：

> 平台向学员提供以下 4 个问题，学员将问题发给平台接入的 AI，AI 自由回答，平台完整保存每份回答原文。
>
> | 编号 | 教学场景 | 问题 |
> | --- | --- | --- |
> | A | 备课核验 | ... |
>
> **设计要求**：
> - 学员提问时不允许添加任何提示或约束，保证 AI 按自身方式回答。
> - 平台保存 AI 回答原文，不修改、不补充。

#### 3.2 判断分类的设计规则

如果该任务需要学员对 AI 输出作判断（如 M01 判断幻觉、M02 评分模型结果），判断分类必须满足：

1. **互斥**：每个对象只能落入一个类别，不能同时属于两类。
2. **按动作分类**：分类对应学员要做的不同操作（保留/替换/删除/收紧），而不是按抽象的"有依据/无依据"分类。
3. **边界用区分点说明**：如果类别之间容易混淆，必须列出"X vs Y"的区分点，说明什么情况归 X、什么情况归 Y。
4. **总体判断由系统汇总**：不让学员对整段内容手选一个总体判断，而是按每个对象的判断结果自动汇总，可多标。

**M01 的四分类**（可采用/需修正/需删除/需限定）是按"教师应对动作"分类的范本。其他任务的判断分类不一定要用这四个，但必须遵循上述 4 条规则。

其他任务可能的判断分类示例：

| 任务 | 判断分类示例 | 分类依据 |
| --- | --- | --- |
| M02 多模型对比 | 优于/相当/劣于（对比基准模型） | 按质量对比结果 |
| M04 教案编制 | 可实施/需调整/不可实施 | 判断教案活动能否直接用于课堂 |
| M05 命题与审校 | 清楚/需调整/不清楚；明确/需调整/不明确；已核对/未核对 | 分别判断题干、答案和各项核验事实 |
| M07 学情分析 | 结论有据/结论需限定/结论无据 | 按分析结论是否有数据支撑 |

#### 3.3 小组复核小节的写法

如果该任务协作方式含"小组复核/小组互评/小组共评"，§3 的最后一个小节必须是"小组复核"。写法见 M01 §3.5 范本，必须说明：

- 学员向小组提交什么。
- 小组成员复核什么、记录什么意见。
- 被复核对象如何选择（下拉菜单、仅本组、不可手填）。
- 小组共同成果是什么、数量要求多少。

同时在 `小组复核功能设计.md` 的"任务字段模板机制"一节补充该任务的 `GroupReviewTemplate`，包括：

- `taskId` / `taskName` / `targetScope` / `requireRoleConfirm` / `minRecords`
- `fields`：每个字段的 key / label / type / required / options / helpText / requiredWhen
- `passRule`：哪些字段必须取特定值才算有效复核

**字段类型从以下 7 种中选用**（见 `小组复核功能设计.md` §二.2）：

`text` / `longtext` / `enum` / `multiselect` / `rating` / `boolean` / `reference`

不得发明新类型。如果现有类型不够用，先在 `小组复核功能设计.md` 中扩展类型定义，再在任务模板中使用。

---

### §4 评分逻辑

**写什么**：把三日方案中该任务的"任务专用评分项"翻译成"平台校验方式"。

#### 4.1 评分标准表

**必须**是一张三列表，比三日方案多一列"平台校验方式"：

| 任务过程质量标准 | 本任务 2 分要求 | 平台校验方式 |
| --- | --- | --- |
| 操作完成与核心步骤 | （从三日方案复制） | 平台能自动检查的具体条件 |
| 教学场景适配 | （从三日方案复制） | 平台能自动检查的具体条件 |
| 专业准确与证据 | （从三日方案复制） | 平台能自动检查的具体条件 |
| 人工核验与迭代 | （从三日方案复制） | 平台能自动检查的具体条件 |
| 隐私、版权、伦理与安全 | （从三日方案复制） | 平台能自动检查的具体条件 |

**"本任务 2 分要求"列**：逐字复制三日方案，不改写。

**"平台校验方式"列**：这是用户故事新增的内容，必须说明平台靠什么数据判断该维度是否达到 2 分。校验方式必须：

1. **可自动执行**：不能写"由评委判断"，要写"对照记录不少于 3 行""依据来源列均非空"这类系统可检查的条件。
2. **对应具体字段**：引用 §5 成果数据结构中的字段名。
3. **覆盖硬门槛**：三日方案规定"专业准确与证据""人工核验与迭代""隐私版权伦理与安全"三项必须 2 分，校验方式必须能判定这三项是否达标。

#### 4.2 参考事实/示例数据

如果该任务的评分需要对照"真实情况"（如 M01 的参考事实、M02 的模型输出标准答案），必须在本节提供。

**每个参考事实必须包含**：

| 内容 | 说明 |
| --- | --- |
| 幻觉/错误表现 | AI 在这个场景下可能产生什么错误 |
| 真实情况 | 逐条列出真实事实，每条可独立核验 |
| 评分设计要点 | 平台据此判定什么情况算什么分类 |

**写法要求**：

- 真实情况必须**逐条列出**，每条可独立核验，不写大段叙述。
- 评分设计要点必须**对应 §3 的判断分类**，说明什么表现归入哪一类。
- 如果任务不涉及"对照真实情况"（如 M03 提示词迭代），本节可写"本任务不涉及参考事实，评分依据为提示词版本的完整性和变化说明"。

---

### §5 成果数据结构

**写什么**：用表格定义平台要为每位学员保存哪些成果字段。

**每个成果一张表**，表头固定为：

| 字段 | 类型 | 说明 |
| --- | --- | --- |

**类型**从以下中选用：`string` / `text` / `int` / `enum` / `enum[]` / `boolean` / `datetime` / `reference`。

**写法要求**：

1. **学员标识字段**：如果成果是个人级的，第一行写 `学员标识 | string | 姓名、组号`；如果是小组级的，第一行写 `组号 | string | 小组标识`。
2. **字段名用中文**：与 §3 和 §4 中引用的字段名保持一致。
3. **enum 类型必须列出候选项**：在说明列中写出所有可选值，如 `enum | 需修正 / 需删除 / 需限定`。
4. **enum[] 类型用于多标**：如总体判断可同时含多个标签时用 `enum[]`。
5. **reference 类型说明指向什么**：如 `reference | 指向该学员的某条对照记录`。
6. **每条成果的字段必须能支撑 §4.1 的平台校验方式**：如果评分要查"依据来源列均非空"，成果表里就必须有"依据来源"字段。

**范本**（M01 成果 2 对照记录）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| 学员标识 | string | 姓名、组号 |
| 序号 | int | 自动编号 |
| 内容编号 | enum | A / B / C / D |
| 原内容 | text | AI 回答中需修正的内容摘录 |
| 判断 | enum | 需修正 / 需删除 / 需限定 |
| 问题类型 | enum | 错误步骤 / 编造内容 / 无依据引用 / 过度推断（由判断自动预填） |
| 依据来源 | text | 文件名称、检索数据库或规范条目 |
| 教师修正后内容 | text | 修正后的内容 |
| 修正理由 | text | 修正依据和理由 |

## 四、编写流程

编写一个任务的用户故事时，按以下步骤操作：

1. **读三日方案**：找到该任务在第六部分的详情，复制标签表到 §2。
2. **写设计意图**：根据三日方案的"教学场景"和"核心知识点"，用 3 段话写 §1。
3. **拆功能**：把三日方案的"操作任务"逐条翻译成平台功能小节，每个操作步骤一个小节。
4. **定判断分类**：如果任务涉及判断，按 §3.2 的 4 条规则设计分类，列出互斥区分点。
5. **配小组复核**：如果协作方式含小组，按 §3.3 写复核小节，并在 `小组复核功能设计.md` 中配模板。
6. **写评分校验**：把三日方案的评分项复制到 §4.1 前两列，第三列"平台校验方式"根据 §3 和 §5 的字段填写。
7. **提供参考事实**：如果评分需要对照真实情况，按 §4.2 逐条编写。
8. **定成果结构**：按 §5 规则定义每个成果的字段表，确保能支撑 §4.1 的校验。
9. **自检**：用本文件第五节的自检清单逐项检查。

## 五、自检清单

编写完成后，逐项检查。任一项不通过则需修改：

| 序号 | 检查项 | 通过标准 |
| --- | --- | --- |
| 1 | 结构完整 | 5 节齐全，标题和顺序与 §三一致 |
| 2 | 标签准确 | §2 标签表与三日方案逐字一致 |
| 3 | 功能可实现 | §3 每个功能小节有功能描述、具体内容、设计要求三部分 |
| 4 | 判断互斥 | §3 的判断分类无交叉，列出了区分点 |
| 5 | 总体判断自动汇总 | 如有判断，总体判断由系统汇总，不让学员手选单一类别 |
| 6 | 小组复核已配 | 协作方式含小组时，§3.5 和 `小组复核功能设计.md` 模板均已配 |
| 7 | 评分可自动校验 | §4.1 第三列每一行都是系统可自动检查的条件，不依赖人工判断 |
| 8 | 硬门槛覆盖 | "专业准确与证据""人工核验与迭代""隐私版权伦理与安全"三项的校验方式能判定是否 2 分 |
| 9 | 参考事实可核验 | §4.2 的真实情况逐条列出，每条可独立核验 |
| 10 | 成果字段支撑校验 | §5 每个成果表的字段能支撑 §4.1 中引用它的校验条件 |
| 11 | 字段类型合规 | §5 只使用了规定的类型（string/text/int/enum/enum[]/boolean/datetime/reference） |
| 12 | 不偏离三日方案 | 操作步骤、阶段成果、评分项均与三日方案一致，未自行增删 |
