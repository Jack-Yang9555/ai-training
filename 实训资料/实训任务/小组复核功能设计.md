# 小组复核功能设计

> 面向实训平台开发人员。说明通用小组复核组件的数据模型、字段模板机制、角色确认流程和角色自动推断规则，用于支撑三日方案中 M01—M12、E01—E06 和 G01—G03 的小组协作与交叉核验需求。
>
> 依据：[《高职教师 AI 实操培训三日方案》](../培训方案/高职教师AI实操培训三日方案.md) §四"分组协作与教学实施"、§五"成果验收与评价"。

## 一、设计目标与约束

| 约束 | 来源 | 处理方式 |
| --- | --- | --- |
| 姓名等身份信息登录时已有 | 用户要求 | 复核记录的"复核人"自动取登录态，不让用户手填 |
| 必须先说明所在组的角色 | 用户要求 | 进入复核页第一步：选择/确认今日在本组的角色 |
| 字段随任务变化 | 用户要求 | 每个任务配一份 `GroupReviewTemplate`，声明要填哪些字段 |
| 被复核对象只能从本组选 | 三日方案 §四.1、M01 §3.5 | 下拉菜单由"本组成员列表"驱动，跨组禁选 |
| 复核意见可追溯 | M01 §3.5 | 每条记录强制关联 reviewer / role / target / task / timestamp |
| 角色每日轮换、至少承担 2 种 | 三日方案 §四.1 | 事前分配 + 事后操作推断双轨记录 |

## 二、核心数据模型

### 1. 角色与身份

```ts
// 六种角色，对应三日方案 §四.1
export type GroupRole =
  | "coordinator"    // 协调员
  | "operator"       // 操作员
  | "verifier"       // 核验员
  | "recorder"       // 记录员
  | "presenter"      // 展示员
  | "student-voice"; // 学生体验员

// 登录态已提供的身份，复核时直接引用，不重复输入
export interface SessionIdentity {
  userId: string;
  name: string;        // 姓名
  groupId: string;     // 所在组（登录时已绑定）
  groupName: string;
}

// 本组成员条目，用于"被复核对象"下拉菜单
export interface GroupMember {
  userId: string;
  name: string;
  roleToday: GroupRole | null;  // 当日分配角色，未分配时为 null
  inferredRoles: RoleEvidence[]; // 基于操作自动推断的实际履职角色
}
```

### 2. 字段模板

```ts
// 字段类型枚举，覆盖 M01—M12、E01—E06 的复核需求
export type ReviewFieldType =
  | "text"          // 单行文本
  | "longtext"      // 多行文本
  | "enum"          // 单选
  | "multiselect"   // 多选
  | "rating"        // 0/1/2 评分
  | "boolean"       // 是/否
  | "reference";    // 关联某条个人成果（如 M01 的某条对照记录）

// 模板里单个字段的定义
export interface ReviewFieldSpec {
  key: string;            // 字段键，如 "evidenceAccurate"
  label: string;          // 显示名，如"依据是否准确"
  type: ReviewFieldType;
  required: boolean;
  options?: string[];     // enum/multiselect 时的候选项
  helpText?: string;      // 填写说明
  // reference 类型：指向哪类个人成果，用于下拉选择被复核的具体条目
  referenceTarget?: {
    artifactKind: string; // 如 "m01-correction-record"
  };
  // 条件必填：当另一字段取特定值时本字段必填
  requiredWhen?: {
    fieldKey: string;
    equals: string | string[];
  };
}

// 任务级复核模板，每个任务配一份
export interface GroupReviewTemplate {
  taskId: string;         // 如 "M01"
  taskName: string;
  templateVersion: string; // 模板版本，便于追溯
  // 复核关系类型，决定 target 选择范围
  targetScope:
    | "member"        // 复核某位组员（M01 交叉复核）
    | "group"         // 复核整组（G01—G03 阶段验收）
    | "self";         // 自评（少数任务）
  // 是否要求"先确认角色"——默认 true，可被任务关闭
  requireRoleConfirm: boolean;
  // 该任务最少需提交的复核条数（M01 每人至少核验 1 份他人成果 → 1）
  minRecords: number;
  // 该任务最多可复核的对象数（防止刷分，可选）
  maxRecords?: number;
  // 字段定义
  fields: ReviewFieldSpec[];
  // 复核通过/不通过的判定规则（可选，用于自动汇总）
  passRule?: {
    // 每条记录中某些字段必须取特定值，如"依据是否准确"必须为"准确"
    requiredValues?: Record<string, string | string[]>;
  };
}
```

### 3. 复核记录

```ts
// 一条复核记录（用户提交后落库）
export interface GroupReviewRecord {
  recordId: string;
  taskId: string;
  templateVersion: string;     // 模板版本，便于追溯
  // 复核人（来自登录态，不可手填）
  reviewer: {
    userId: string;
    name: string;
    groupId: string;
  };
  // 复核人在本次复核中承担的角色（进入页面时先确认）
  reviewerRole: GroupRole;
  // 角色来源：事前分配 / 操作推断 / 用户确认
  reviewerRoleSource: "assigned" | "inferred" | "user-confirmed";
  // 被复核对象
  target: {
    kind: "member" | "group" | "self";
    targetUserId?: string;     // member/self 时填
    targetName: string;
    targetGroupId?: string;    // group 时填
  };
  // 按模板填写的字段值
  fieldValues: Record<string, string | string[] | number | boolean>;
  // 时间戳
  submittedAt: string;
  // 状态：草稿 / 已提交 / 被退回
  status: "draft" | "submitted" | "rejected";
}
```

## 三、任务字段模板机制

每个任务维护一份 `GroupReviewTemplate`。模板是"声明式"的：只描述要填什么，不写 UI 逻辑。复核组件读模板 → 渲染表单 → 校验 → 落库。

### 1. M01 模板示例

M01 的判断分类采用"按教师应对动作"的四分类：可采用 / 需修正 / 需删除 / 需限定。四类互斥，由"参考事实中是否有对应条目""内容是否与事实一致""结论是否超出依据范围"三个判定点区分。判断为"可采用"的对象不进入对照记录；其余三类自动进入对照记录并预填问题类型。

```ts
export const M01_REVIEW_TEMPLATE: GroupReviewTemplate = {
  taskId: "M01",
  taskName: "大模型幻觉识别与内容核验",
  templateVersion: "1.1",
  targetScope: "member",
  requireRoleConfirm: true,
  minRecords: 1,
  fields: [
    {
      key: "targetArtifact",
      label: "被复核的对照记录",
      type: "reference",
      required: true,
      referenceTarget: { artifactKind: "m01-correction-record" },
      helpText: "选择该组员提交的某一条对照记录（原内容—判断—修正后—理由）",
    },
    {
      key: "judgmentAppropriate",
      label: "判断分类是否恰当",
      type: "enum",
      required: true,
      options: ["恰当", "应改为可采用", "应改为需修正", "应改为需删除", "应改为需限定"],
      helpText: "复核该组员对原内容作出的四分类判断是否正确",
    },
    {
      key: "evidenceAccurate",
      label: "依据来源是否准确",
      type: "enum",
      required: true,
      options: ["准确", "部分准确", "不准确"],
    },
    {
      key: "correctionReasonable",
      label: "修正是否合理",
      type: "enum",
      required: true,
      options: ["合理", "部分合理", "不合理"],
      helpText: "判断为'需修正'时是否替换为参考事实正确内容；'需删除'时是否删除或标注未找到依据；'需限定'时是否收紧结论",
    },
    {
      key: "omission",
      label: "是否还有遗漏",
      type: "boolean",
      required: true,
    },
    {
      key: "omissionDetail",
      label: "遗漏说明",
      type: "longtext",
      required: false,
      helpText: "上一项选'是'时必填",
      requiredWhen: { fieldKey: "omission", equals: "true" },
    },
    {
      key: "suggestion",
      label: "可执行修改意见",
      type: "longtext",
      required: true,
      helpText: "必须具体可执行，不能只写'建议修改'",
    },
  ],
  passRule: {
    requiredValues: {
      judgmentAppropriate: ["恰当"], // 判断分类必须被复核为恰当
      evidenceAccurate: ["准确", "部分准确"], // 依据不允许"不准确"
      correctionReasonable: ["合理", "部分合理"], // 修正不允许"不合理"
    },
  },
};
```

### 2. M02 模板示例

M02 的协作方式为"个人评分、小组共评"，复核对象是组员的个人多模型评分表和模型选择结果。共评关注评分差异、选择分歧和补充建议。

### 3. 其他任务的模板差异（示意）

M03 的协作方式为“个人完成、小组互评”，复核对象是组员的 V1、V2 和变化说明。互评判断允许为“不明确”，因为这里记录的是事实性检查结果；有效性取决于字段完整和建议可执行，不要求给出正面评价。

    },

    { key: "outputFormatClear", label: "输出格式是否明确", type: "enum", required: true, options: ["明确", "部分明确", "不明确"] },

      key: "suggestion",

当前 Demo 无多人后端时，G01 可独立开始：当前教师优先读取真实有效的本地 M01—M05 成果，缺项使用明确标注且仅在 G01 内有效的任务内演示成果，不得据此生成、补写或反写上游成果、进度或通过状态。其他成员只能使用确定性模拟摘要，并醒目标注“当前为无多人后端的模拟组员成果，不代表真实提交。”人员或分组变化后旧成员引用、交叉检查、贡献完整性和当前通过状态失效，历史验收继续保留。

M06 的个人成果互评对象必须是当前同组其他成员，字段固定为被互评组合成果、教学场景适配、数字人使用合规、视频可播放和可执行建议；“需调整”是有效事实判断，不设置正向值才有效的隐藏规则。作者记录采纳、部分采纳或不采纳的处理依据后形成教师确认组合成果。

M07 的个人成果复核对象同样是当前同组其他成员，字段固定为匿名学情报告、一个明确统计指标、同伴复算值、一致/不一致和复算过程或差异说明。不一致记录仍有效，但作者必须按确定性公式纠正，或记录不采纳的计算依据；不得评价真实学生个人排名、人格、态度或长期能力。

M06、M07 均以 `targetScope: "member"`、`requireRoleConfirm: true`、`minRecords: 1` 实现。复核对象受 `participantId + groupId` 约束；Demo 必须披露组员成果为无多人后端的确定性模拟摘要，人员或分组变化后旧对象和当前教师确认失效，历史验收保留。

## 四、复核流程（角色优先）

```
用户进入任务 X 的"小组复核"入口
        │
        ▼
① 系统从登录态读取: userId / name / groupId
   （不弹窗问姓名，直接用）
        │
        ▼
② 角色确认页（requireRoleConfirm=true 时必经）
   - 展示: 你是 {name}，所在组 {groupName}
   - 系统识别你今天的实际操作: 已提交 2 条复核意见 → 核验员
   - 今日分配角色: 核验员（来自分组管理）
   - 下拉: 请确认你本次复核承担的角色
     候选 = assignedRole（默认）∪ inferredRoles ∪ 六种 GroupRole（兜底手动选）
   - 选定后才能下一步
        │
        ▼
③ 选择被复核对象
   - targetScope=member → 下拉仅本组成员（排除自己），显示"姓名（今日角色）"
   - targetScope=group   → 自动锁定为本组，无需选
   - targetScope=self    → 自动锁定为自己
        │
        ▼
④ 渲染模板字段表单
   - 按 template.fields 逐项渲染
   - reference 字段: 列出被复核对象已提交的对应成果条目供选择
   - 校验 required / requiredWhen / options / passRule
        │
        ▼
⑤ 提交 → 生成 GroupReviewRecord
   - reviewer 来自登录态
   - reviewerRole 来自步骤②
   - reviewerRoleSource 记录角色来源
   - target 来自步骤③
   - fieldValues 来自步骤④
   - 状态默认 submitted
        │
        ▼
⑥ 汇总校验
   - 该用户在本任务下的记录数 ≥ minRecords?
   - 每条记录是否满足 passRule?
   - 不满足 → 标红提示，可补交或修改
```

## 五、角色自动推断

### 1. 设计思路

三日方案 §四.1 要求"角色每日轮换"和"每位教师三天内至少承担 2 种角色"，这是**事前组织行为**。自动打标签是**事后事实归因**。两者并存：

- 事前分配的 `assignedRole` 来自分组管理，反映组织意图。
- 事后的 `inferredRoles` 来自操作日志，反映实际履职。
- 两者对比能发现"挂名不履职"或"未分配却实际承担"的情况。

### 2. 六种角色的可观测操作信号

| 角色 | 可观测操作信号 | 数据来源 |
| --- | --- | --- |
| 协调员 coordinator | 在小组成果工作区创建条目、@组员催交、确认阶段成果全员到齐、发起 G01—G03 验收提交 | 小组成果工作区操作日志 |
| 操作员 operator | 调用 AI 工具生成内容（PPT/数字人/网页/知识库/题目）、提交个人成果的"AI 草稿"版本 | AI 工具调用日志、个人成果提交记录 |
| 核验员 verifier | 提交 `GroupReviewRecord`、提出可执行修改意见、标记他人成果问题 | 小组复核记录 |
| 记录员 recorder | 编辑小组成果文档（核验清单、测试报告、展示页）、提交汇总性成果 | 小组成果文档编辑日志 |
| 展示员 presenter | G02/G03 演示环节主讲标记、演示录像/截图上传、答问记录 | 阶段验收演示记录 |
| 学生体验员 student-voice | 切换学生视角测试 AI 助教、提交 M11 答疑测试反馈、标注"从学生角度"的体验问题 | 视角切换日志、M11 测试记录 |

### 3. 数据结构

```ts
export interface RoleEvidence {
  role: GroupRole;
  triggeredBy: string;        // 触发该标签的具体操作描述
  operationCount: number;     // 操作次数
  lastSeenAt: string;         // 最近一次操作时间
  confidence: "high" | "medium" | "low"; // 置信度
}

// 操作日志统一格式（平台各模块埋点写入）
export interface OperationLog {
  userId: string;
  groupId: string;
  category: string;     // 操作类别，见下表
  detail?: string;      // 操作细节
  at: string;           // 时间戳
  taskId?: string;      // 关联任务（可选）
}

// 事前分配与事后推断的合并视图
export interface MemberRoleAssignment {
  userId: string;
  name: string;
  groupId: string;
  date: string;                  // 哪一天
  assignedRole: GroupRole;       // 事前分配的预期角色
  inferredRoles: RoleEvidence[]; // 基于操作自动推断的实际履职角色
  mismatch?: {
    type: "nominal-only" | "unassigned-but-acted";
    detail: string;
  };
}
```

操作日志 `category` 取值：

| category | 含义 | 用于推断 |
| --- | --- | --- |
| `ai-generate` | 调用 AI 工具生成内容 | operator |
| `group-review-submit` | 提交小组复核记录 | verifier |
| `group-artifact-edit` | 编辑小组成果文档 | recorder |
| `group-artifact-create` | 创建小组成果条目 | coordinator |
| `stage-submit` | 发起 G01—G03 阶段验收提交 | coordinator |
| `member-mention` | @组员催交或分工 | coordinator |
| `stage-demo` | 阶段演示主讲 | presenter |
| `demo-upload` | 上传演示录像/截图 | presenter |
| `perspective-switch` | 切换学生/教师视角 | student-voice（detail=student 时） |
| `m11-test-submit` | 提交 M11 答疑测试反馈 | student-voice |

### 4. 判定规则

每条规则独立，可叠加——一个人可同时持有多个角色标签，对应方案里"人数不足时允许兼任"。

```ts
export interface RoleInferenceRule {
  role: GroupRole;
  test: (ops: OperationLog[]) => RoleEvidence | null;
}

export const ROLE_INFERENCE_RULES: RoleInferenceRule[] = [
  {
    role: "operator",
    test: (ops) => {
      const aiCalls = ops.filter(o => o.category === "ai-generate");
      return aiCalls.length >= 3
        ? { role: "operator", triggeredBy: "AI工具调用≥3次",
            operationCount: aiCalls.length,
            lastSeenAt: aiCalls.at(-1)!.at, confidence: "high" }
        : null;
    },
  },
  {
    role: "verifier",
    test: (ops) => {
      const reviews = ops.filter(o => o.category === "group-review-submit");
      return reviews.length >= 1
        ? { role: "verifier", triggeredBy: "提交≥1条复核意见",
            operationCount: reviews.length,
            lastSeenAt: reviews.at(-1)!.at, confidence: "high" }
        : null;
    },
  },
  {
    role: "recorder",
    test: (ops) => {
      const edits = ops.filter(o => o.category === "group-artifact-edit");
      return edits.length >= 2
        ? { role: "recorder", triggeredBy: "编辑小组成果文档≥2次",
            operationCount: edits.length,
            lastSeenAt: edits.at(-1)!.at, confidence: "high" }
        : null;
    },
  },
  {
    role: "coordinator",
    test: (ops) => {
      const coordOps = ops.filter(o =>
        o.category === "group-artifact-create" ||
        o.category === "stage-submit" ||
        o.category === "member-mention"
      );
      return coordOps.length >= 2
        ? { role: "coordinator", triggeredBy: "创建组成果/发起阶段提交/@组员≥2次",
            operationCount: coordOps.length,
            lastSeenAt: coordOps.at(-1)!.at, confidence: "medium" }
        : null;
    },
  },
  {
    role: "presenter",
    test: (ops) => {
      const demos = ops.filter(o => o.category === "stage-demo" || o.category === "demo-upload");
      return demos.length >= 1
        ? { role: "presenter", triggeredBy: "阶段演示/上传演示材料",
            operationCount: demos.length,
            lastSeenAt: demos.at(-1)!.at, confidence: "high" }
        : null;
    },
  },
  {
    role: "student-voice",
    test: (ops) => {
      const voiceOps = ops.filter(o =>
        (o.category === "perspective-switch" && o.detail === "student") ||
        o.category === "m11-test-submit"
      );
      return voiceOps.length >= 1
        ? { role: "student-voice", triggeredBy: "切换学生视角测试/提交答疑测试",
            operationCount: voiceOps.length,
            lastSeenAt: voiceOps.at(-1)!.at, confidence: "medium" }
        : null;
    },
  },
];

// 应用所有规则，返回该用户在指定日期的实际履职角色
export function inferRoles(ops: OperationLog[]): RoleEvidence[] {
  return ROLE_INFERENCE_RULES
    .map(rule => rule.test(ops))
    .filter((e): e is RoleEvidence => e !== null);
}
```

### 5. 事前分配与事后推断的对比

| 情况 | 含义 | 处理 |
| --- | --- | --- |
| `assignedRole` ∈ `inferredRoles` | 分配了也实际做了 | 正常履职 |
| `assignedRole` ∉ `inferredRoles` 且 `inferredRoles` 非空 | 分配了没做，做了别的 | 标记"挂名"，按实际履职评分 |
| `inferredRoles` 含未分配角色 | 没分配但实际承担了 | 记录为"实际贡献"，纳入协作评分 |
| `inferredRoles` 为空 | 什么都没做 | 角色履行维度 0 分 |

### 6. 对复核流程的影响

角色确认页（流程步骤②）改为：

```
进入复核页
   │
   ▼
系统展示: 你是 {name}，第 {n} 组
   今日分配角色: 核验员（来自分组管理）
   系统识别你今天的实际操作: 已提交 2 条复核意见 → 核验员
   ───────────────────────────────
   复核角色将记录为: 核验员
   [确认] [我实际承担的是其他角色 ▼]
```

- 默认取 `assignedRole`，如果与 `inferredRoles` 一致就直接确认。
- 不一致时允许用户从 `inferredRoles` 里选一个"我实际承担的角色"，或保留分配角色。
- `reviewerRoleSource` 记录角色来源（`assigned` / `inferred` / `user-confirmed`），便于追溯。
- 这样既尊重事前组织，又承认实际行为，且留痕可追溯。

## 六、与其他模块的衔接

| 模块 | 关系 |
| --- | --- |
| 登录态 | 提供 `userId / name / groupId`，复核组件只读，不让用户改 |
| 分组管理 | 提供 `GroupMember[]`，驱动"被复核对象"下拉；角色轮换表提供 `assignedRole` |
| 操作埋点 | 各模块按 `OperationLog` 格式写入操作日志，驱动角色自动推断 |
| 个人成果档案 | `reference` 字段从这里取被复核的具体条目（如 M01 的某条对照记录） |
| 任务过程评分 | "人工核验与迭代""有效交叉核验"两个维度的证据直接来自 `GroupReviewRecord` |
| 小组协作评分 | "角色履行""有效交叉核验""协作修改"维度从 `MemberRoleAssignment` + 复核记录 + 后续修改闭环中抽取 |

## 七、关键设计决策

1. **角色确认放在最前**：满足"先说明所在组角色"的要求；角色是复核记录的必填属性，不是装饰。若今日角色已在分组管理里分配，则默认选中但仍允许修改（兼任场景）。
2. **姓名不手填**：`reviewer` 三字段全部来自登录态，UI 上只读展示"复核人：张三（第 3 组）"。
3. **模板而非硬编码**：新任务只加一份 `GroupReviewTemplate`，不改组件代码。字段类型用枚举收口，避免模板泛滥。
4. **被复核对象锁本组**：`targetScope=member` 时下拉数据源严格按 `groupId` 过滤，前端 + 后端双校验。
5. **reference 字段串联个人成果**：复核不是空填表，而是指向被复核人的具体某条成果，这样"修改闭环"才能成立（反馈→定位到某条→本人修改→前后版本留痕）。
6. **passRule 可选**：M01 要求"依据准确+修正合理"才能算有效核验，这种硬门槛写进模板，不散落在评分代码里。
7. **角色推断是只读的**：自动标签不修改 `assignedRole`，只生成 `inferredRoles` 供展示和评分参考。
8. **阈值可调**：`>=3 次`、`>=2 次` 这类阈值放进配置，不同任务可调，避免硬编码。
9. **兼任天然支持**：规则之间独立，一个人同时触发多条就同时持有多个标签，对应方案里"人数不足时允许兼任"。
